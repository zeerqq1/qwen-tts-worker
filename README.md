# Qwen3-TTS на RunPod Serverless

Тот же движок, что и локально, только на арендованной видеокарте.
Платишь посекундно за генерацию, в простое — ноль.

## Почему без сетевого тома

Модель (4.2 ГБ) запечена **внутрь образа**. Альтернатива — сетевой том — стоит
денег каждый месяц независимо от того, работаешь ты или нет, и оставляет за
собой состояние, которое надо чистить.

Схема здесь такая, что чистить нечего в принципе:

* модель — в образе, кешируется на воркере после первой загрузки;
* референс голоса едет **в самом запросе** (~500 КБ);
* готовый звук возвращается **в ответе** и умирает вместе с задачей;
* файловая система контейнера исчезает после выполнения.

Ни тома, ни бакета, ни накопления. Ровно то, что нужно.

## Шаг 1. Собрать и залить образ

Нужен установленный Docker и аккаунт на Docker Hub.

```
cd runpod_worker
docker build -t <твой-логин>/qwen-tts-worker:1 .
docker push <твой-логин>/qwen-tts-worker:1
```

Сборка тянет 4.2 ГБ весов — первый раз это минут десять. Образ выходит ~13 ГБ.

Если Docker ставить не хочется — RunPod умеет собирать из GitHub-репозитория:
залей туда папку `runpod_worker/` и на шаге 2 выбери «Deploy from GitHub»
вместо образа.

## Шаг 2. Создать эндпоинт

RunPod → Serverless → New Endpoint.

| Настройка | Значение | Почему |
|---|---|---|
| Container image | `<логин>/qwen-tts-worker:1` | |
| GPU | 24 ГБ (RTX 4090) или 80 ГБ (A100/H100) | см. таблицу скорости ниже |
| Max workers | 3–5 | это и параллелизм, и потолок расходов |
| Active workers | **0** | иначе платишь за простой |
| Idle timeout | 30–60 с | воркер доживает до следующей пачки, не платя за холодный старт заново |
| Container disk | 25 ГБ | образ + запас |
| Network volume | **не подключать** | не нужен, только деньги |
| Execution timeout | 900 с | |

Переменные окружения (необязательно):

* `QWEN_COMPILE=1` — включает `torch.compile` (по умолчанию включён).
  На Linux он работает штатно, в отличие от Windows, и даёт заметный прирост.
  Первая задача на свежем воркере компилируется ~1–2 минуты, дальше быстро.
  Поставь `0`, если что-то пойдёт не так.
* `QWEN_MODEL_DIR` — путь к весам внутри образа, менять не нужно.

## Шаг 3. Подключить студию

Создай `runpod.json` в корне проекта (рядом с `app.py`):

```json
{
  "api_key": "<ключ из RunPod → Settings → API Keys>",
  "endpoint_id": "<id эндпоинта>"
}
```

В интерфейсе переключи **«Где генерировать» → «Облако»**.

Файл в `.gitignore` не попадает автоматически — не выкладывай его никуда.

## Что происходит при запуске

Студия режет работу на задачи примерно по 55 секунд звука каждая (это держит
JSON-ответ в разумных пределах) и **отправляет их все разом**. RunPod ставит
лишние в очередь и раздаёт по мере освобождения воркеров — то есть чем больше
`Max workers`, тем шире распараллеливание. Это и есть главное преимущество
облака перед одной локальной картой.

Каждая задача возвращает FLAC — без потерь и вдвое компактнее сырого PCM.
Студия распаковывает его и пишет WAV точно так же, как при локальной работе:
те же 0.12 с воздуха в начале, столько же в конце, сколько задано ползунком,
и микрозатухание на срезе.

Кнопка «Остановить» **отменяет задачи на стороне RunPod**, а не просто перестаёт
их ждать — иначе они продолжали бы тикать по счётчику.

## Сколько это стоит

Serverless тарифицируется посекундно. Ставки RunPod:

| GPU | $/час | Пропускная память |
|---|---|---|
| RTX 4090 (24 ГБ) | 1.10 | 1008 ГБ/с |
| L40S (48 ГБ) | 1.75 | 864 ГБ/с |
| A100 (80 ГБ) | 2.72 | 2039 ГБ/с |
| H100 (80 ГБ) | 4.79 | 3350 ГБ/с |

Модель упирается в пропускную способность памяти, а объём памяти определяет
размер батча — поэтому A100 и H100 быстрее не «немного», а в разы. И поскольку
платишь за секунды, дорогая карта не обязательно дороже за работу: она просто
заканчивает раньше.

## Диагностика

```
python -c "import runpod_client as c; print(c.health())"
```

Покажет, сколько воркеров занято, свободно и в очереди. Если ключ неверный —
скажет прямо.
